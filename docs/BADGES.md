# Бейджи grapeGram

## Источник истины

Публичный репозиторий, каталог `data/`:

- `badge_users.json` — кому какой бейдж выдан;
- `owner_users.json` — ровно два административных ID;
- `signatures/*.sig` — отделённые подписи Ed25519 (base64, одна строка);
- `schemas/*.schema.json` — проверка структуры.

## Чтение (клиент)

1. Запрос `badge_users.json`, `owner_users.json` и `.sig` (одним пакетом).
2. Проверка подписи публичным
   ключом из `data/keys/grapegram_ed25519.pub.pem` (вшит в APK) над байтами файла.
3. Проверка схемы и `version`; откат к более старой версии запрещён
   (`version` и `updated_at` не должны уменьшаться).
4. Только после успеха — запись в кэш и применение.
5. Нет сети → используется последний проверенный кэш; кэша нет → бейджи не
   показываются.
6. Обновление: при старте, при возврате из долгого фона (не чаще 1 раза в
   час), вручную. При открытии профиля сеть не дёргается.

Отображение — по Telegram ID (в чатах, шапке, профиле, участниках). Если ID
недоступен — бейдж не показывается. Имена и аватары не используются.

## Запись (только владельцы)

Клиент не может выдавать бейджи. Схема:

```
App -> POST /challenge                (сервер выдаёт одноразовый код, TTL 5 мин)
User -> бот: /bind <код>              (бот получает настоящий from.id)
Server -> POST /bind {code}           (сервер сверяет ID с owner_users.json)
Server -> POST /admin/grant|revoke    (сессия + owner-check + подпись + commit)
Server -> GitHub: badge_users.json + .sig + история
App -> GET (подписанные данные) -> проверка -> отображение
```

- Telegram ID берётся **из апдейта бота**, а не из тела запроса приложения.
- Код одноразовый, живёт 5 минут, привязан к сессии.
- Приватный ключ и GitHub-токен — только на сервере (или в GitHub Secrets).
- В APK — только публичный ключ.

## Почему не локальный флаг

Локальную проверку ID можно обойти модифицированным клиентом. Поэтому
право на запись подтверждается сервером через бота, а данные становятся
валидными только после подписи. Клиент проверяет подпись, а не «наличие ID
в JSON».

## Формат подписи

- Алгоритм: Ed25519 (`openssl pkeyutl -rawin`).
- Подписываются точные байты опубликованного файла (как он лежит в `data/`).
- `.sig` = base64 от 64 байт.
- SHA-256 используется только для целостности артефактов, **не** как замена
  подписи.

## Ротация ключей

1. Сгенерировать новую пару (`scripts/gen_keys.py`).
2. Опубликовать новый публичный ключ рядом со старым (`data/keys/`).
3. Клиент принимает подпись любым из ключей, помеченных как `active`.
4. После обновления приложений старый ключ помечается `retired`.
5. Приватный ключ старой пары уничтожается.

## Тесты (см. `tests/`)

Получение, показ чужого бейджа, отсутствие у постороннего, отказ не-владельцу,
поддельная подпись, повреждённый JSON, офлайн, обновление, откат версии,
повтор challenge, применение устаревшего файла, совместимость с Premium
(визуально не перекрывает официальный значок).
